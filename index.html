대회 제출 파이프라인

요구사항: ① 제출 POST가 성공으로 반환됐다면 실제로도 성공이어야 한다. ② (user, problem, codeHash)는 중복 없이 처리한다. 평균 10ms이지만 p999가 2초까지 벌어지는 채점 API 앞에서, 이 두 가지를 지키는 구조를 찾는 과정이다.

최종 아키텍처 (V5)

ACK 전에 consumer가 죽으면 메시지는 자동 재전달되고, DB unique constraint가 중복 반영을 막는다.

  1. contest_submission과 채점 발행용 outbox를 같은 DB 트랜잭션으로 저장한다.
  2. outbox relay가 RabbitMQ quorum queue에 메시지를 발행한다.
  3. publisher confirm을 받은 시점에 outbox를 PUBLISHED로 표시한다 — 완료의 의미는 "채점 완료"가 아니라 "RabbitMQ가 작업을 인수함"이다.
  4. consumer는 메시지를 받아 직접 채점 API를 호출한다.
  5. 채점 결과와 스코어보드 outbox를 DB 트랜잭션으로 저장한다.
  6. DB commit이 성공한 후 manual ACK를 보낸다.
  7. consumer 프로세스나 connection/channel이 ACK 전에 종료되면 메시지는 다시 전달된다.

진화 과정 — 6번의 재설계

V0

event + async

유실 발생

Spring의 event + async 구조. POST 시 DB에 저장하고 이벤트 발행, 리스너가 채점 API를 호출해 결과를 갱신한다.

POST→ DB insert→ event→ listener→ 채점 API→ UPDATE
PROBLEM
  • 중간 프로세스가 죽으면 제출이 유실된다 — 요구사항 ① 위반.
  • 고부하에서 쓰루풋이 낮다.
V1

JPA batch insert

부분 개선

insert를 큐에 모아 같은 EntityManager에서 persist — MySQL batch rewrite를 활용해 POST 반환까지의 쓰루풋을 개선했다.

POST→ in-mem queue→ batch persist→ 채점 API→ UPDATE
PROBLEM
  • 레이턴시 증가. batch 내 한 건 실패 시 포함된 insert 전체가 실패.
  • 채점 구간은 여전히 느리다.
V2

judge one transaction

지연 전파

채점 쓰루풋 개선을 위해 한 트랜잭션에서 SKIP LOCKED로 여러 건을 읽고, 스레드풀에서 API 호출 후 한 번에 insert.

PROBLEM
  • 트랜잭션 범위가 너무 크다.
  • 가끔 오는 p999(2초) 제출 하나가 트랜잭션에 묶인 전체 batch에 지연을 전파한다.
V3

judge claim

1차 채택 → 한계

submission과 result 테이블을 분리하고 과정 사이에 큐를 넣어 트랜잭션을 짧게 유지. p999 지연이 다른 제출로 퍼지지 않는다. 복구·중복 방지를 위해 claim 칼럼(claim_key, claimed_at, status)을 두고, 오래된 미완료 claim은 sweeper가 다시 큐에 넣는다.

claim UPDATE→ queue→ 채점 API→ queue→ result batch insert
PROBLEM
  • p999가 평균의 200배인 상황에서 claimed_at 기반 실패 판단은 딜레마다 — timeout을 짧게 잡으면 중복 채점이 늘고, 길게 잡으면 장애 복구가 늦어진다.
V4

DB outbox + Kafka

복잡도 초과

append-only log처럼 쓰이는 submission에 Kafka를 도입. claim이 시간 변동이 큰 채점 API 앞이 아니라 Kafka로 보내는 짧은 구간 앞으로 이동해 timeout 설정이 수월해졌다. 유니크 제약 보장을 위해 DB 저장은 유지.

DB insert→ claim→ Kafka→ 채점 API→ result→ offset commit 관리
PROBLEM
  • 같은 partition 앞쪽의 느린 작업이 뒤 작업의 commit을 막는다 — 완료 offset을 별도 저장하고 연속 완료 지점을 계산하는 수동 commit 관리가 필요했다.
  • DB claim과 offset commit을 함께 관리하며 코드 복잡도가 크게 상승, 채점 쓰루풋도 감소.
V5

RabbitMQ 작업 큐

ACCEPTED

채점은 과거 이벤트를 여러 consumer가 재생하는 스트림이 아니라, 하나의 작업을 하나의 worker가 가져가 처리하고 성공 여부를 개별적으로 알리는 작업 큐다. 일부 채점만 최대 2초까지 느려질 수 있으므로, 완료 순서가 달라져도 각각 독립적으로 완료 처리할 수 있어야 한다.

Kafka Share는 레코드별 ACK와 재전달로 이 문제를 상당 부분 해소하지만, 현 프로젝트는 replay·다중 consumer group·장기 로그 보존을 쓰지 않는데 새 Kafka/Spring Kafka 버전 도입과 운영 비용이 붙는다. RabbitMQ는 메시지별 ACK, prefetch, consumer 간 작업 분배가 기본 모델이라 현재 채점 작업과 더 직접적으로 맞았다.

중복 처리 — at-least-once + 멱등

DB 저장 성공 직후 ACK 전 장애가 나면 메시지는 다시 전달된다. exactly-once를 기대하지 않고 멱등 처리로 흡수한다.

  • submissionId + judgeVersion에 unique constraint
  • 이미 결과가 존재하면 재저장하지 않음
  • 같은 채점이 진행 중이면 기존 실행 결과를 기다리거나 재사용
  • 재채점은 별도의 judgeRunId로 구분

영속성

  • durable quorum queue + persistent message — 과반 replica 복제 후 confirm 반환
  • publisher confirm + consumer manual ACK
  • 3개 이상의 서로 다른 RabbitMQ 노드

재시도와 복구

  • 일시적 채점 서버 오류는 지연 후 재시도, 반복 실패는 DLQ로 — 같은 queue 즉시 재투입으로 인한 retry loop 차단
  • 대회 재채점은 별도 queue/worker capacity 사용
  • 완료 판단은 "queue가 비었는가"가 아니라 DB의 rejudge_run 전체 대상 대비 완료 수로

트레이드오프

RabbitMQ는 Kafka보다 producer batching, 압축, 대규모 backlog와 replay에 불리하고, quorum queue + publisher confirm은 복제·디스크 기록 비용으로 처리량이 감소한다. 하지만 이 시스템의 병목은 브로커가 아니라 평균 10ms, 최대 2초의 채점 API다. 느린 채점이 다른 작업에 지연을 전파하지 않고, 실패한 작업을 단순하게 재분배할 수 있는지가 더 중요했다. 그 대가로 claim의 heartbeat/sweeper와 Kafka offset commit 관리가 사라지고, RabbitMQ cluster 운영·DLQ 관리·멱등 처리 책임이 생겼다.

결정 요약

DB-only 구조(V3)는 별도 인프라 없이 batch 성능이 좋았지만 claim, heartbeat, sweeper를 직접 구현해야 했고, 채점 지연 편차가 커서 stale claim timeout을 짧게 잡으면 중복 채점이 늘고 길게 잡으면 복구가 늦어졌다. DB outbox + Kafka(V4)는 높은 처리량과 replay가 가능했지만 완료 순서가 뒤섞인 offset commit을 직접 관리해야 했고, 현 시스템에서는 Kafka 로그의 장점보다 복잡성 증가가 더 컸다.

최종적으로 DB를 제출과 결과의 원본으로 유지하고, RabbitMQ quorum queue가 채점 작업의 분배와 in-flight 상태를 관리하도록 역할을 나눴다.

MySQL
제출, 결과, unique constraint, 재채점 진행 상태 — 정합성의 원본
RabbitMQ
작업 분배, backpressure, 미완료 작업 재전달
Redis
스코어보드와 채점 결과 캐시
Outbox
DB 저장과 RabbitMQ 발행 사이의 유실 방지

DB의 정합성과 RabbitMQ의 작업 큐 모델을 결합해, 기존 claim/heartbeat/sweeper와 Kafka의 연속 offset commit 관리를 모두 제거했다.

02

데드락 해결 과정

대회 입력 → 최종화 실행, 대회 중 일반 제출 병행, 스케일 아웃을 겹쳐 돌리자 데드락이 발생했다. 외래키 제거와 데이터 접근 순서 정렬만으로는 해결되지 않는 케이스가 있었고, 세 단계에 걸쳐 잡았다.

Case 1 — REPEATABLE READ → READ COMMITTED

-- claim: id 증가 방향으로 gap 락 → 레코드 락
UPDATE contest_submission
SET judge_status = 'PROCESSING'
WHERE judge_status = 'PENDING'
ORDER BY id LIMIT 100;

-- insert: 반대로 레코드 락 이전에 gap 락
INSERT INTO contest_submission (..., judge_status='PENDING', ...) VALUES (...);
TX A · claim UPDATE
gap lock (id↑)→record lock
⇄ 교차 대기
TX B · INSERT
record lock→gap lock
실선 = 보유한 락, 점선 = 대기 중인 락. 1씩 증가하는 키를 썼는데도 실제로는 claim 쪽이 더 큰 id의 락을 잡고 있었다.

고려하지 못한 순서 변동과 InnoDB 내부 락 순서가 겹쳐 데드락이 났다. 격리 수준을 READ COMMITTED로 변경해 claim UPDATE가 gap 락을 잡지 않게 했다.

Case 2 — UPDATE WHERE … → SELECT FOR UPDATE + UPDATE BY id

-- 오래 처리되지 못한 submission 복구
UPDATE contest_submission
SET judge_status = 'PENDING'
WHERE judge_status = 'PROCESSING' AND judge_claimed_at < ?
ORDER BY judge_claimed_at, id LIMIT ?;

-- 처리 완료 기록
UPDATE contest_submission
SET judge_status = 'DONE'
WHERE id = ? AND judge_status = 'PROCESSING' AND judge_claim_token = ?;

row 순서를 ORDER BY에 맞춰 정렬하면 해결될 것으로 봤지만, 실제로는 한쪽은 secondary index부터, 다른 쪽은 primary key부터 락을 타면서 데드락이 계속됐다. 그래서 바로 UPDATE하지 않고 두 단계로 나눴다.

  • SELECT … FOR UPDATE SKIP LOCKED로 대상 id를 먼저 고른 뒤
  • 양쪽 모두 id 기반 UPDATE를 수행

Case 3 — 인덱스 제거

그런데도 SELECT FOR UPDATE SKIP LOCKED 뒤의 UPDATE에서 데드락이 다시 터졌다. UPDATE가 수정하는 secondary index에 락이 일시적으로 걸렸다 풀리는데, 이것이 다른 row 수정과 교차했다 — 한쪽은 (status, claimed_at, id)를 잡고 (status, id)를 기다리고, 다른 쪽은 반대였다. 현재 쿼리 패턴에서는 (status, claimed_at, id)만으로 충분했기에 (status, id) 인덱스를 제거하고 로직을 정리해 해결했다.

교훈 — MySQL InnoDB에서는 예상하기 어려운 데드락이 쉽게 발생한다. 락 순서를 코드 레벨에서 맞추는 것만으로는 부족하며, 인덱스 락 경로까지 확인하고 데드락이 나더라도 회복 가능한 구조(재시도, 멱등)를 함께 설계해야 한다.

03

스코어보드 회복

스코어보드는 대회 중 빠른 제공을 위해 Redis 위에 올렸다(데이터 구조가 DB에 부적합). 문제는 Redis 유실 시의 복구다 — snapshot 복구를 전제하면, outbox id는 중간에 빈 숫자가 있을 수 있고 도착 순서도 id와 다를 수 있어 어떤 outbox가 도착하지 않았는지 사전에 알 수 없다. go-back-N 같은 복구가 불가능한 상황.

Redis seq ACCEPTED

Redis가 1씩 증가하는 seq를 발급·저장한다. 이미 본 제출이면 기존 seq를 반환, 처음이면 새로 발급. 이 seq를 outbox에도 기록한다.

Redis가 과거 snapshot으로 복구되면 같은 seq가 재발급되고, outbox에서 seq 중복으로 이를 감지할 수 있다. 주기적으로 중복을 검사해 재시도하면 자동 복구된다.

PROS
  • Redis에 상태를 묻는 과정 없이 outbox 갱신만으로 회복
CONS
  • 복구가 새 submission 제출(트래픽)에 직접적으로 의존

Gapless seq REJECTED

빈틈없는 seq를 생성하면 어떤 outbox가 누락됐는지 알 수 있고, Redis가 처리한 seq 목록을 유지하면 복구 가능. Kafka 같은 append log 기반 저장소면 파티션 내 gapless 발급이 쉽다.

PROS
  • 복구에 트래픽이 필요 없음
CONS
  • 이것만을 위해 Kafka를 도입하기 어려움
  • DB에서 gapless 유지는 seq 발급 구간의 직렬화 필요
  • 복구를 여러 서버에서 돌리기 어려움

DB만 사용하는 현 구성에서 gapless seq의 직렬화 비용이 우려되어 Redis seq를 선택했다. 대회 종료 시점에는 한 번 더 대사(reconciliation)를 돌려 최종 정합성을 확보한다.

04

랭킹 조회 개선

사용자는 랭킹 페이지에서 자기 위치를 확인하고, 자신이 포함된 페이지로 바로 이동할 수 있어야 한다. ORDER BY … LIMIT :offset, :limit은 정렬 인덱스를 타더라도 깊은 페이지에서 앞의 row를 전부 읽고 버려야 한다.

solved — bucket 집계 계산형

solved_count_bucket 테이블에 [푼 문제 수 n, 해당 count의 유저 수, 그보다 큰 유저 수]를 유지한다.

  • 내 solved count → bucket에서 상위 유저 수 조회
  • 같은 count 내 내 순번 계산 → 합산해 rank 산출
  • rank가 속한 page start 계산 → 해당 구간만 읽기

solved_count가 1씩 증가만 하기 때문에 가능한 구조 — 전체 재정렬 없이 작은 bucket 테이블만으로 rank를 계산한다. 단, 성능이 유저 수만이 아니라 값의 분포에 좌우된다.

current streak — snapshot 사전계산형

자정 배치가 전날 활동으로 streak를 갱신한 뒤, 0이 아닌 유저만 모아 user_streak_rank_snapshot을 만든다. rank가 이미 저장되어 있다.

  • snapshot에서 내 row와 snapshot_rank를 바로 읽기
  • snapshot_rank BETWEEN start AND end로 페이지 조회

조회 시점에 rank를 계산하는 것이 아니라 읽기만 하는 구조. streak는 매일 바뀌므로 일 단위 snapshot과 자연스럽게 맞는다.

벤치마크
