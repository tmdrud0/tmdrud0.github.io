처음 이 블로그에 올라온 글들은 대부분 성능 최적화나 복구 설계처럼 특정 문제를 깊게 파고드는 내용이었다.  
그래서 프로젝트를 처음 보는 사람 입장에서는 "그래서 이 서비스가 전체적으로 뭘 하는 건데?"가 먼저 궁금할 수 있다.

이번 글은 그런 질문에 답하기 위한 개요 글이다.  
이 프로젝트가 어떤 온라인 저지 서비스를 목표로 하고 있는지, 어떤 기능이 있고, 왜 구조를 이렇게 나눴는지 큰 흐름만 먼저 정리해 보려 한다.

## 한 줄로 설명하면

이 프로젝트는 **문제 풀이, 제출, 채점 결과 반영, 랭킹 조회, 대회 스코어보드**를 제공하는 온라인 저지 서비스다.

사용자 입장에서 보면 다음 흐름으로 이해하면 된다.

- 문제 목록을 보고
- 특정 문제에 코드를 제출하고
- 채점 결과를 확인하고
- 정답 수나 스트릭 기반 랭킹을 보고
- 대회 중이면 실시간에 가까운 스코어보드를 확인한다

겉으로는 익숙한 온라인 저지지만, 내부적으로는 "제출 쓰기 경로", "랭킹 deep page 조회", "Redis 스코어보드 복구"처럼 병목과 운영 이슈가 빨리 드러나는 구조이기도 하다.

## 서비스가 하는 일

핵심 기능은 크게 다섯 가지다.

### 1. 문제와 제출 관리

- 문제 목록 조회
- 문제 상세 조회
- 제출 폼 제공
- 제출 내역 조회

여기까지는 일반적인 저지 서비스의 기본 기능이다.  
이 프로젝트에서는 특히 제출이 많이 몰리는 상황을 중요한 운영 시나리오로 본다.

### 2. 채점 결과 반영

사용자가 코드를 제출하면 끝이 아니라, 이후에 채점 결과가 들어오고 그 결과에 따라 사용자 상태가 갱신된다.

예를 들면:

- 문제를 처음 맞힌 경우 solved count 증가
- 제출 결과 저장
- 대회 중이면 스코어보드 반영용 outbox 생성

즉 제출은 단일 insert 한 번으로 끝나는 작업이 아니라, 뒤쪽의 여러 상태 변화를 유발하는 시작점에 가깝다.

### 3. 랭킹 조회

이 프로젝트는 단순 목록 조회보다도 "내가 포함된 페이지로 바로 가기" 같은 랭킹 UX를 중요하게 본다.

그래서 일반적인 `OFFSET` 기반 deep paging이 느려지는 문제를 해결하려고:

- solved count bucket
- streak snapshot

같은 구조를 도입했다.

### 4. 대회 스코어보드

대회 중에는 제출 결과가 반영되면서 스코어보드가 빠르게 갱신되어야 한다.  
이 부분은 조회 성능 때문에 Redis를 적극적으로 사용한다.

하지만 Redis는 원본 저장소가 아니라 파생 상태이기 때문에, 장애 후 복구 설계도 같이 따라와야 한다. 이 블로그의 다른 글들이 이 주제를 다루는 이유도 여기에 있다.

### 5. 성능 검증

이 프로젝트는 단순 CRUD 앱처럼 만들고 끝내는 방향보다, 병목을 의도적으로 드러내 보고 검증하는 방향에 가깝다.

그래서 별도 성능 실험 코드와 설정이 들어 있다.

- Gatling 기반 부하 테스트
- perf 프로필
- 단일 서버 / 역할 분리 서버 시나리오

즉 기능 구현과 함께 "어디서 무너지는가"를 계속 측정하는 프로젝트라고 볼 수 있다.

## 구조는 어떻게 나뉘어 있나

아래 그림이 현재 구조를 가장 단순하게 요약한 것이다.

![온라인 저지 구조도](/assets/images/posts/project-overview-architecture.svg)

이 그림을 기준으로 보면 역할은 이렇게 나뉜다.

### Web

사용자가 직접 붙는 애플리케이션이다.

- Thymeleaf 기반 화면 제공
- 로그인/회원 관련 흐름
- 문제/제출/랭킹/대회 페이지 제공
- 제출 요청 수신

기본적으로 사용자가 보는 대부분의 HTTP 요청은 여기로 들어온다.

### MySQL

원본 데이터 저장소다.

- 사용자
- 문제
- 제출
- 채점 결과
- 랭킹 계산에 필요한 데이터
- 스코어보드 반영용 outbox

이 프로젝트에서 정합성의 기준은 기본적으로 MySQL이다.

### Redis

조회 가속과 운영 보조를 위한 저장소다.

- 세션 저장
- 제출 중복 제어/속도 제한 보조
- 대회 스코어보드

특히 스코어보드는 Redis에서 빠르게 읽고, 원본 반영 근거는 DB와 outbox 쪽이 들고 있는 구조다.

### Judge

채점 관련 비동기 작업을 담당하는 역할이다.

제출 직후 모든 걸 동기 처리하기보다, 채점과 후속 반영을 분리해 부하와 책임을 나누는 방향을 취하고 있다.

### Batch

운영성 작업과 후처리를 맡는 역할이다.

- outbox 소비
- Redis scoreboard 반영
- 복구 replay
- streak 배치
- snapshot 생성

즉 웹 요청 경로에서 직접 하기 부담스러운 작업을 뒤쪽으로 넘겨 흡수한다.

## 패키지 기준으로 보면

코드도 기능 단위로 나누어져 있다.

- `contest`
  - 대회, 스코어보드, outbox, 대회 제출 관련 로직
- `problem`
  - 문제 조회와 문제 관련 화면
- `submission`
  - 일반 제출, 채점 이벤트, 제출 후처리
- `user`
  - 사용자 정보, 프로필, 랭킹, streak
- `auth`
  - 인증 관련 구성
- `perf`
  - 성능 실험용 엔드포인트와 테스트 보조 코드

이렇게 나누면 "도메인별로 무엇이 책임인지"를 따라가기 쉽고, 나중에 성능 이슈를 볼 때도 어느 기능 축에서 문제가 생기는지 분리해서 보기 편하다.

## 왜 서버 역할을 나누려고 했나

설정 파일을 보면 단일 서버 모드뿐 아니라 역할 분리 프로필도 들어 있다.

- `multi-web`
- `multi-batch`
- `multi-judge`

이렇게 나누는 이유는 단순히 서버를 많게 만들기 위해서가 아니다.

목적은 더 명확하다.

- 사용자 요청을 받는 경로와
- 시간이 조금 걸려도 되는 후처리/배치 작업과
- 채점 같은 별도 워크로드를

서로 덜 간섭하게 만들기 위해서다.

예를 들어:

- 제출이 몰릴 때 Web 서버는 최대한 빨리 요청을 받고
- Judge는 채점 작업을 담당하고
- Batch는 scoreboard 반영과 복구, 랭킹성 배치를 맡는 식이다

즉 "기능 분리"보다 "부하 성격 분리"에 더 가깝다.

## 이 프로젝트에서 특히 중요한 지점

이 프로젝트를 그냥 온라인 저지 구현이 아니라, 운영 관점에서 흥미롭게 만드는 지점은 세 가지다.

### 1. 제출은 가장 뜨거운 쓰기 경로다

대회 중에는 많은 요청이 한 경로에 집중된다.  
그래서 제출 저장 경로는 단순 기능이 아니라, 시스템 전체의 체감 성능을 좌우하는 핵심 경로가 된다.

### 2. 랭킹은 조회지만 데이터가 커지면 금방 비싸진다

처음에는 단순 정렬과 페이징으로 충분해 보이지만, 유저 수가 커지면 `OFFSET` 비용이 금방 커진다.  
이 프로젝트는 그 문제를 bucket과 snapshot으로 줄이려는 실험을 담고 있다.

### 3. Redis는 빠르지만 복구까지 설계해야 한다

스코어보드를 Redis에 두면 조회는 빨라진다.  
대신 장애 후 "무엇을 기준으로 다시 맞출 것인가"를 같이 설계해야 한다.

즉 빠른 시스템은 저장 구조만 아니라, 복구 구조까지 포함해서 봐야 한다.

## 앞으로 이 블로그에서 보게 될 내용

이 개요 글 이후의 포스트들은 대부분 이 큰 구조 안에서 특정 문제를 깊게 파고든 내용들이다.

- 제출 저장 경로를 bulk insert로 바꾼 이유
- Redis scoreboard를 어떻게 복구할지
- around me 랭킹 조회를 어떻게 줄였는지

즉 이 글은 지도이고, 나머지 글들은 그 지도 안의 특정 지점을 자세히 설명하는 기록이라고 보면 된다.

## 마무리

정리하면 이 프로젝트는 단순히 문제 제출 페이지를 만드는 데서 끝나는 온라인 저지가 아니다.

- 제출이 몰릴 때 쓰기 경로가 어떻게 버티는지
- 랭킹이 커질 때 조회가 어떻게 무너지지 않게 할지
- Redis 기반 파생 상태를 어떻게 복구할지

같은 운영 문제를 함께 다루는 구조를 실험하는 프로젝트에 가깝다.

그래서 앞으로 개별 글을 읽을 때는, "한 기능의 세부 구현"이라기보다 **온라인 저지를 운영 가능한 구조로 만들기 위한 한 조각**이라고 보면 흐름이 훨씬 잘 잡힐 것이다.
